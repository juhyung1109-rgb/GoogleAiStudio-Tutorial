01

Git의 탄생 — 리눅스 커널과 열흘

Git은 버전 관리 도구를 만들자고 시작된 프로젝트가 아니었다. 리눅스 커널 개발이 갑자기 멈출 위기에 놓였고, 그것을 풀기 위해 급하게 만들어진 도구였다.

사건 — 커널 개발이 멈출 뻔했다

리눅스 커널은 1991년부터 전 세계 개발자들이 이메일로 패치를 주고받으며 만들어 왔다. 참여자가 수천 명으로 늘자 손으로 감당할 수 없게 되었고, 2002년부터 BitKeeper라는 상용 도구를 “오픈소스 개발에는 무료”라는 조건으로 쓰기 시작했다.

그런데 2005년, 그 무료 사용 권한이 철회되었다. 커널 개발자 한 명이 BitKeeper의 동작 방식을 분석하려 한 일이 라이선스 위반 논란으로 번진 것이다. 수천 명이 함께 쓰던 도구가 하루아침에 사라질 상황이었다.

리누스 토르발스는 대안을 찾는 대신 직접 만들기로 했다. 2005년 4월 7일 첫 커밋이 기록되었고, 열흘쯤 뒤에는 이미 커널 개발에 실제로 쓸 수 있는 수준이 되었다. 그리고 넉 달 뒤인 8월, 그는 이 프로젝트를 하마노 준이오(Junio Hamano)에게 넘겼다. 하마노는 지금까지 20년 넘게 Git을 관리하고 있다.

이름의 유래

git은 영국 속어로 ‘멍청이·못난 놈’이라는 뜻이다. 리누스는 “나는 이기적인 놈이라 내 프로젝트에 전부 내 이름을 붙인다”고 농담했다. 리눅스(Linux)에 이어 두 번째다.

급하게 만들었지만 설계는 분명했다

지금 Antigravity 화면에서 누르는 버튼들도 결국 이때 정해진 네 가지 목표 위에 얹혀 있다. 왜 이렇게 동작하는지를 알면 버튼도 명령도 훨씬 덜 낯설다.

설계 목표지금 우리가 겪는 결과
분산 (distributed)모든 사람이 기록 전체의 사본을 갖는다 → 인터넷이 끊겨도 커밋·되돌리기가 되고, 서버가 사라져도 코드가 남는다
속도수천 명의 패치를 감당해야 했다 → 커밋·브랜치 전환이 거의 즉시 끝난다
무결성 (해시)커밋마다 a1b2c3d… 같은 문자열이 붙는다. 파일이 한 글자라도 바뀌면 값이 달라져 손상을 즉시 알아챈다
비선형 개발브랜치를 만들고 합치는 일이 흔해야 했다 → 상태 표시줄에서 클릭 한 번으로 갈래가 생긴다

“SHA-1 해시는 애초에 보안을 위한 것이 아니었다. 손상을 찾아내기 위한 것이었다.”

— Linus Torvalds, Git 20주년 인터뷰 (2025)

그래서 지금은 어디에 쓰이나

커널 하나를 위해 만든 도구가 소프트웨어를 만드는 거의 모든 곳의 기본기가 되었다. Antigravity 같은 AI 개발 도구들이 하나같이 Git을 기본으로 품고 나오는 이유이기도 하다.

지표규모
GitHub 사용자1억 8천만 명 이상 — 2025년 한 해에만 3,600만 명이 새로 가입했고, 평균 1초에 한 명씩 늘고 있다
저장소 수6억 3천만 개 — 1분에 230개씩 새로 만들어진다
2025년 커밋9억 8,600만 건 (전년 대비 +25%)
AI 관련 저장소430만 개 — 2023년의 두 배 가까이로 늘었다
바이브 코딩과 Git

에이전트에게 맡겨 코드를 만들다 보면 어느 순간부터 되돌릴 수 없게 되는 일이 흔하다. “아까까지는 됐는데”가 반복된다면 그건 실력 문제가 아니라 기록을 남기지 않아서다. 잘 돌아가는 지점마다 커밋해 두면, 에이전트에게 마음 놓고 크게 고쳐 보라고 시킬 수 있다. Git은 AI와 함께 일할 때 오히려 더 필요해진 도구다.

02

Antigravity 화면 지도 — Git이 어디에 있나

Antigravity는 VS Code 계열 편집기라 Git 기능이 이미 화면에 들어 있다. 따로 프로그램을 열 필요 없이 왼쪽 아이콘 하나면 된다. 먼저 늘 보게 되는 기본 화면부터 읽어 보자.

1 2 3 4 5

실제로 프로젝트 폴더를 열어 둔 화면. Antigravity는 VS Code 계열이라 아이콘 배치와 메뉴 이름이 위 화면과 같다. 아직 소스 제어 패널을 열지 않은, 늘 보게 되는 기본 상태다.

번호 · 무엇인가Git의 눈으로 보면
① 소스 제어 아이콘활동 막대 위에서 세 번째, 가지가 갈라진 모양. Ctrl/Cmd + Shift + G로도 열린다. 고친 파일이 생기면 이 아이콘에 숫자 배지가 붙는다 — 위 화면처럼 배지가 없으면 아직 저장소가 아니거나 고친 것이 없다는 뜻이다
② 열려 있는 탭왼쪽 탭이 .gitignore. 저장소를 만들자마자 가장 먼저 만드는 파일이며, 여기에 적힌 것은 GitHub에 올라가지 않는다(7장)
③ __pycache__파이썬이 자동으로 만들어 내는 폴더. 사람이 쓴 코드가 아니고 지워도 다시 생기므로 올리지 않는다. .gitignore에 적어 두면 소스 제어 패널의 변경 목록에 아예 나타나지 않는다
④ .gitignore무시할 것들을 한 줄에 하나씩 적은 목록. 이 파일 자체는 커밋해서 함께 공유한다 — 같은 저장소를 받은 사람 모두가 같은 규칙을 쓰게 된다
⑤ output_news.wav프로그램이 만들어 낸 결과물. 용량이 크고 코드를 실행하면 다시 생기므로 올리지 않는다. 데이터·모델·이미지 결과물도 마찬가지다
설정 폴더(.vscode · .antigravity)는 어떻게 하나

위 화면의 .vscode/settings.json처럼 편집기 설정 폴더는 판단이 갈린다. 파이썬 인터프리터 지정처럼 수강생 모두가 같이 쓰면 좋은 설정은 커밋하고, 개인 경로나 키가 들어간 파일은 .gitignore로 제외한다. 애매하면 커밋 전에 파일을 한 번 열어 보고 결정한다.

① 아이콘을 누르면 화면이 이렇게 바뀐다

소스 제어 패널이 열리고, 커밋에 필요한 것이 전부 이 한 칸에 모인다. 아래는 그 상태를 그린 것이다.

번호 · 위치하는 일
⑥ 커밋 메시지 상자“무엇을 했는가”를 쓰고 커밋. 상자 옆 ✨ 아이콘을 누르면 변경 내용을 읽고 메시지를 AI가 대신 써 준다
⑦ 변경 사항 목록파일 이름을 클릭하면 전후 비교(diff)가 열린다. M=수정, U=새 파일, D=삭제. ＋를 누르면 스테이지에 올라간다
⑧ 내장 터미널Ctrl + `로 열린다. 버튼으로 안 되는 일은 여기서 git 명령으로 한다
⑨ 상태 표시줄맨 아래 왼쪽에 현재 브랜치 이름. 클릭하면 브랜치 전환·생성. 그 옆 ↻ 화살표가 GitHub와 주고받을 커밋 개수이자 동기화 버튼이다

Git과 GitHub, 그리고 Antigravity

Git — 기록하는 프로그램

컴퓨터에 설치되는 도구. 인터넷 없이도 동작하며, Antigravity의 소스 제어 버튼들은 결국 이 Git을 대신 눌러 주는 것이다.

GitHub — 올려두는 서비스

기록을 인터넷에 보관하고 공유하는 곳. 계정이 필요한 부분은 여기부터다.

Antigravity — 둘을 다루는 창구

편집기 안에서 커밋·업로드·되돌리기를 버튼으로 하게 해 준다. 에이전트가 고친 내용을 검토하는 화면도 여기다.

이 문서를 읽는 방법

앞으로 모든 작업은 “Antigravity에서”를 먼저, “터미널에서”를 그 아래에 나란히 적었다. 수업에서는 버튼으로 익히고, 원리를 설명할 때 명령을 보여 주는 순서를 권한다. 두 방법은 완전히 같은 일을 하며, 섞어 써도 아무 문제가 없다.

03

준비 — Git 설치 확인과 첫 설정

Antigravity에 Git이 내장되어 있지는 않다. 컴퓨터에 Git이 깔려 있어야 소스 제어 패널이 동작한다. 딱 한 번만 확인하면 된다.

  1. 내장 터미널을 연다

    Ctrl + ` (백틱, 숫자 1 왼쪽). Antigravity 아래쪽에 터미널 패널이 열린다. Windows는 PowerShell, macOS는 zsh가 기본이다.

  2. 설치 여부 확인
    Antigravity 내장 터미널
    $ git --version
git version 2.55.0   ← 이렇게 나오면 설치돼 있다

    버전이 안 나오면 Git을 먼저 설치한다. Windows는 git-scm.com의 설치 파일, macOS는 xcode-select --install 또는 brew install git. 자세한 절차는 〈Git 첫 걸음〉 문서에 정리해 두었다.

  3. 이름과 이메일 등록 — 한 번만

    모든 커밋에 이 정보가 새겨진다. 설정하지 않으면 첫 커밋에서 오류가 난다.

    첫 설정
    $ git config --global user.name "Heejin Park"
$ git config --global user.email "park0122@example.com"
$ git config --global init.defaultBranch main

# 줄바꿈 문자 — 윈도우와 맥이 섞인 수업에서는 꼭 맞춰 둔다
$ git config --global core.autocrlf true    # Windows
$ git config --global core.autocrlf input   # macOS

$ git config --list                        # 확인
  4. 폴더를 열어 둔다

    Antigravity의 Open Folder로 작업 폴더(예: python-lab)를 연다. 소스 제어 패널은 “지금 열려 있는 폴더”를 기준으로 동작하므로, 폴더를 열지 않으면 아무것도 표시되지 않는다.

설정 확인이 먼저인 이유

Git이 없거나 이름이 등록되지 않은 상태에서 소스 제어 패널을 누르면 “Git not found”나 “Please tell me who you are”가 뜬다. 수업 첫 시간에 이 세 줄을 다 같이 실행해 두면 그날 남은 시간을 벌 수 있다.

04

GitHub 회원가입 — 5분이면 끝난다

브라우저에서 github.com/signup에 접속한다. 화면이 한 줄씩 순서대로 물어보는 방식이라 그대로 따라가면 된다.

  1. 이메일 주소

    오래 쓸 이메일을 넣는다. 인증 메일이 오고, 비밀번호를 잊었을 때 유일한 복구 수단이 된다. 학교 이메일은 졸업하면 못 쓰게 되는 경우가 있으니 개인 메일을 권한다.

  2. 비밀번호

    15자 이상, 또는 숫자와 소문자를 섞어 8자 이상이어야 통과된다.

  3. 사용자 이름(username) — 가장 신중하게

    내 GitHub 주소가 된다. github.com/사용자이름이 곧 명함이자 포트폴리오 주소다.

    https://github.com/signup
    Username heejin-park 영문·숫자·하이픈(-)만 가능 · 39자 이내 · 하이픈으로 시작하거나 끝날 수 없다
    Continue
    이름 짓기 요령

    취업·발표에서 그대로 보여줄 이름으로 짓는다. 나중에 이름을 바꾸면 기존 저장소 주소가 모두 달라진다. 이름-성, 성이름dev 처럼 담백한 형태가 무난하다.

  4. 퍼즐 · 이메일 인증 코드

    간단한 그림 퍼즐을 풀고, 메일로 온 여덟 자리 숫자를 입력한다. 안 보이면 스팸함을 확인한다. 이메일 인증을 마치지 않으면 저장소를 만들 수 없다.

  5. 요금제 — Free를 고른다

    수업과 개인 프로젝트에는 Free로 충분하다. 무료 계정도 비공개(private) 저장소를 개수 제한 없이 만들 수 있다.

가입 직후 해 두면 좋은 설정

① 이메일 숨기기 — Settings → Emails에서 Keep my email addresses private를 켠다. 커밋에 실제 메일 주소가 공개되는 것을 막아 준다.

켰다면 GitHub가 알려 주는 대체 주소를 Antigravity 터미널에서 git에 등록해 둔다. 그래야 커밋이 내 계정 활동으로 정상 집계된다.

내장 터미널
$ git config --global user.email "12345678+heejin-park@users.noreply.github.com"
05

Antigravity에 GitHub 계정 연결하기

가입만으로는 편집기가 내 계정을 알지 못한다. 한 번 연결해 두면 이후 업로드·내려받기에서 아무것도 묻지 않는다.

방법 ① 편집기에서 로그인 — 가장 간단

  1. 계정 아이콘 누르기

    왼쪽 활동 막대 맨 아래 사람 모양 아이콘 → Sign in with GitHub. 브라우저가 열리고 Authorize를 누르면 편집기로 돌아온다.

  2. 또는 업로드할 때 자동으로

    연결하지 않은 상태에서 Publish to GitHub를 누르면 그 자리에서 로그인 창이 뜬다. 미리 하지 않아도 흐름이 끊기지 않는다.

  3. 확인

    계정 아이콘에 내 GitHub 아이디가 표시되면 끝. 이제 소스 제어 패널에서 저장소 생성·업로드가 모두 가능하다.

터미널파를 위한 대안 — gh CLI

편집기 로그인 대신 터미널에서 gh auth login을 써도 된다. 브라우저 승인 방식이라 토큰을 직접 만들 필요가 없고, 둘 중 하나만 해 두면 충분하다.

내장 터미널
# 설치 — 운영체제에 맞는 한 줄
$ winget install --id GitHub.cli   # Windows
$ brew install gh                  # macOS

$ gh auth login                   # 화면 안내 → 브라우저에서 승인
✓ Logged in as heejin-park

2단계 인증(2FA)은 지금 켜 두는 편이 낫다

GitHub는 기여 활동이 있는 계정(패키지 배포, 릴리스 생성, 조직 소유 등)을 골라 2FA 의무 대상으로 지정한다. 안내 메일을 받으면 45일 안에 설정해야 하고, 유예 기간이 지나면 2FA를 켜기 전까지 접속이 막힌다. 수업 도중 갑자기 막히는 것보다 미리 켜 두는 쪽이 낫다.

  1. 인증 앱 설치

    Google Authenticator, Microsoft Authenticator, 1Password 등. 기기를 바꿔도 백업되는 앱이면 더 좋다.

  2. GitHub에서 QR 띄우기

    프로필 사진 → Settings → Password and authentication → Enable two-factor authentication.

  3. 복구 코드를 반드시 저장

    휴대폰을 잃었을 때 계정에 들어갈 유일한 열쇠다. 내려받아 따로 보관한다. 저장소에 커밋하는 것은 금물이다.

터미널에서 비밀번호를 물어본다면

GitHub는 2021년부터 계정 비밀번호로 push를 받지 않는다. 비밀번호를 입력하라는 화면이 나오면 인증이 아직 안 된 것이다. 위의 편집기 로그인이나 gh auth login을 먼저 한다. 굳이 토큰을 쓰겠다면 Settings → Developer settings → Personal access tokens에서 발급받아 비밀번호 자리에 붙여넣으면 되지만, 수업에서는 권하지 않는다(발급·보관·만료 관리가 번거롭다).

06

저장소 시작하기

상황은 둘 중 하나다. 내 폴더가 이미 있는가, 아니면 GitHub에 있는 것을 받아 오는가.

Antigravity에서

  1. 폴더를 연다

    File → Open Folder로 작업 폴더를 연다.

  2. 저장소로 만든다

    소스 제어 패널(Ctrl/Cmd+Shift+G) → Initialize Repository. 폴더 안에 숨김 폴더 .git이 생기고, 이 폴더가 곧 저장소가 된다.

  3. .gitignore부터 만든다

    다음 장의 내용을 먼저 처리한다. 첫 커밋 전에 해야 한다.

  4. 첫 커밋

    메시지 상자에 첫 커밋이라 쓰고 커밋. “스테이지된 변경 사항이 없다”고 물으면 전부 스테이지할지 묻는 것이니 예를 누른다.

  5. GitHub에 올린다

    같은 패널의 Publish Branch 또는 Publish to GitHub. 공개(public)로 할지 비공개(private)로 할지를 묻고, 저장소 생성부터 업로드까지 한 번에 끝난다.

    브라우저에서 저장소를 미리 만들 필요가 없다

    편집기가 GitHub에 저장소를 대신 만들어 준다. 먼저 만들어 두었다가 README 때문에 첫 업로드가 거부되는 흔한 사고를 아예 피할 수 있다.

같은 일을 터미널에서 하면

내장 터미널
$ git init                        # Initialize Repository
$ git add .                        # 변경 사항의 ＋ 버튼
$ git commit -m "첫 커밋"          # ✓ 커밋 버튼
$ git branch -M main

# Publish to GitHub 버튼이 하는 일 = 아래 두 줄
$ gh repo create python-lab --private --source=. --push
# 또는 브라우저에서 빈 저장소를 만든 뒤
$ git remote add origin https://github.com/heejin-park/python-lab.git
$ git push -u origin main

Antigravity에서

  1. 주소를 복사한다

    GitHub 저장소 페이지의 초록색 <> Code 버튼 → HTTPS 주소 복사.

  2. 복제한다

    시작 화면의 Clone Repository, 또는 명령 팔레트(Ctrl/Cmd+Shift+P)에서 Git: Clone. 주소를 붙여넣고 저장할 폴더를 고르면 된다.

    GitHub 계정을 연결해 두었다면 주소를 붙여넣는 대신 내 저장소 목록에서 골라 받을 수도 있다.

  3. 바로 작업 시작

    복제한 폴더는 origin 연결이 이미 끝나 있다. 이후로는 커밋하고 동기화만 누르면 된다.

같은 일을 터미널에서 하면

내장 터미널
$ git clone https://github.com/heejin-park/python-lab.git
$ cd python-lab
수업에서는 이쪽을 권한다

강사가 만든 실습 저장소를 학생들이 각자 clone해서 시작하면, 폴더 구조·.gitignore·README가 처음부터 통일된다. 첫 시간의 사고가 눈에 띄게 줄어든다.

07

.gitignore 먼저 — 올리면 안 되는 것들

모든 파일을 기록할 필요는 없다. 특히 API 키가 든 파일은 절대 올라가면 안 된다. 저장소를 만들자마자 가장 먼저 하는 일이다.

Antigravity에서 프로젝트 폴더 맨 위에 .gitignore 파일을 새로 만들고 아래 내용을 붙여넣는다. 저장하는 순간 소스 제어 패널의 변경 목록에서 해당 파일들이 사라진다.

.gitignore — 파이썬 + Antigravity 기본형
# 비밀 — 가장 중요하다
.env
.env.*
!.env.example

# 파이썬
__pycache__/
*.pyc
.ipynb_checkpoints/
venv/
.venv/

# 데이터·모델 (용량이 크다)
data/

*.pkl

# 편집기·운영체제 잡파일
.vscode/
.DS_Store
Thumbs.db
.antigravity 폴더는 올릴까, 말까

Rules 파일처럼 팀·수강생과 공유할 값어치가 있는 설정은 커밋하는 편이 낫다. 같은 규칙 아래에서 에이전트가 같은 스타일의 코드를 만들어 주기 때문이다. 다만 그 폴더 안에 키·토큰·개인 경로가 들어간 파일이 있다면 그 파일만 .gitignore에 따로 적어 제외한다. 커밋 전에 소스 제어 패널에서 내용을 한 번 열어 보고 결정한다.

.gitignore는 '이미 올린 파일'에는 듣지 않는다

한 번이라도 커밋된 파일은 나중에 목록에 적어도 계속 추적된다. 터미널에서 추적을 끊어야 한다.

추적 해제
$ git rm --cached .env
$ git commit -m "remove .env from tracking"
$ git check-ignore -v .env   # 규칙이 출력되면 정상

그리고 이미 GitHub에 올라간 키는 커밋을 지워도 기록에 남는다. 키 자체를 폐기하고 새로 발급받는 것이 먼저다.

08

매일의 흐름 — 스테이지 · 커밋 · 동기화

파일은 네 개의 장소를 거쳐 움직인다. 소스 제어 패널의 버튼들은 각각 “어디에서 어디로 옮기는가”에 대응한다.

왜 '대기실'이 따로 있나

에이전트가 파일 10개를 고쳤는데 그중 3개만 남기고 싶다면, 그 3개만 골라 기록할 수 있어야 한다. ＋ 버튼은 “이건 이번 기록에 넣자”라는 표시일 뿐, 아직 저장된 것이 아니다. 저장은 커밋 버튼이 한다.

Antigravity에서 — 네 박자

  1. 확인 — 무엇이 바뀌었나

    소스 제어 아이콘의 숫자 배지가 고친 파일 수다. 파일 이름을 클릭하면 왼쪽이 이전, 오른쪽이 지금인 비교 화면이 열린다. 커밋 전에 이 화면을 훑는 습관이 사고를 막는다.

  2. ＋ 로 담기

    파일 옆 ＋는 그 파일만, “변경 사항” 제목 옆 ＋는 전부 담는다. 파일 일부만 담고 싶으면 비교 화면에서 줄을 선택해 Stage Selected Ranges를 쓴다.

  3. 메시지를 쓰고 커밋

    상자에 “무엇을 했는가”를 한 줄로. ✨ 아이콘을 누르면 변경 내용을 읽어 메시지를 자동으로 만들어 준다(명령 팔레트에서는 Generate Commit Message). 생성된 문장은 그대로 쓰지 말고 한 번 다듬는다 — 무엇을 바꿨는지는 잘 적지만 왜 바꿨는지는 모르기 때문이다.

  4. 동기화

    Sync Changes 또는 상태 표시줄의 ↻ 화살표. 받아올 것과 보낼 것을 한 번에 처리한다(pull 다음 push).

같은 일을 터미널에서 하면

내장 터미널
$ git status                       # 소스 제어 패널을 여는 것과 같다
$ git add .                        # ＋ 버튼
$ git commit -m "로그인 기능 추가"   # ✓ 커밋 버튼
$ git pull && git push           # ↻ 동기화 버튼

$ git log --oneline                # 기록 훑어보기 (q로 빠져나온다)
$ git diff                         # 아직 담지 않은 변경 내용
한 번에 끝내는 단축키 만들기

매번 네 번 누르는 게 번거롭다면 스테이지 → AI 메시지 생성 → 커밋 → 동기화를 단축키 하나에 묶을 수 있다. 명령 팔레트에서 Preferences: Open Keyboard Shortcuts (JSON)을 열고 아래를 추가한다.

keybindings.json
[
  {
    "key": "ctrl+enter",
    "command": "runCommands",
    "args": {
      "commands": [
        "git.stageAll",
        "antigravity.generateCommitMessage",
        "git.commitAll",
        "git.sync"
      ]
    },
    "when": "scmInputIsFocused"
  }
]

익숙해진 다음에 쓴다. 처음부터 자동화하면 각 단계가 무엇을 하는지 배우지 못한 채 손만 빨라진다.

커밋 메시지 쓰는 법

나중에 이 목록만 보고 원하는 시점을 찾아야 한다. “무엇을 했는가”를 한 줄로 쓴다. 수정, ㅇㅇ, update는 나중의 나를 괴롭힌다. 의미 있는 한 덩어리를 끝냈을 때마다 커밋하는 것이 좋은 습관이다.

09

에이전트와 함께 쓰는 Git

여기가 Antigravity에서 Git을 쓸 때 가장 다른 지점이다. 코드를 고치는 주체가 내가 아닐 때, 커밋은 기록이 아니라 안전벨트가 된다.

가장 흔한 사고

“에이전트에게 기능 하나를 더 붙여 달라고 했더니, 잘 돌아가던 부분까지 같이 바뀌어 전부 망가졌다.” 커밋해 두지 않았다면 돌아갈 지점이 없다. 이 사고는 실력이 아니라 순서의 문제다.

네 가지 습관

① 시키기 전에 커밋

에이전트에게 작업을 맡기기 직전에 커밋한다. 지금 이 상태가 “돌아올 지점”이 된다.

메시지는 작업 전 저장 정도면 충분하다.

② 결과는 diff로 검토

에이전트가 끝났다고 하면 실행해 보기 전에 소스 제어 패널부터 연다. 건드리지 말라고 한 파일이 목록에 있는지 본다.

③ 큰 실험은 브랜치에서

구조를 바꾸는 작업은 새 브랜치를 만들어 맡긴다. 실패하면 브랜치째 버리면 그만이다.

④ 성공하면 즉시 커밋

“됐다!” 하는 순간이 커밋 시점이다. 그 상태를 붙잡아 두어야 다음 작업을 과감하게 시킬 수 있다.

실제 리듬

에이전트와 일하는 한 사이클
# ① 지금 잘 돌아가는 상태를 붙잡아 둔다
$ git add . && git commit -m "로그인까지 정상 동작"

# ② 에이전트에게 작업을 맡긴다 (Editor View에서 프롬프트)
#    "회원가입 화면을 추가해줘. app.py는 건드리지 말고 signup.py에 새로 만들어줘."

# ③ 무엇이 바뀌었는지 확인한다 — 소스 제어 패널 또는
$ git status
$ git diff

# ④-A 마음에 들면 커밋
$ git add . && git commit -m "회원가입 화면 추가"

# ④-B 마음에 안 들면 통째로 되돌린다 (커밋 이후의 변경만 사라진다)
$ git restore .
Rules에 커밋 규칙을 적어 두기

Antigravity의 Rules 파일에 아래 같은 문장을 넣어 두면, 에이전트가 매번 같은 방식으로 협조한다.

“파일을 수정하기 전에 무엇을 바꿀지 먼저 요약해서 알려줘. 여러 파일을 동시에 고칠 때는 파일별로 이유를 적어 줘. .env와 키가 든 파일은 절대 열거나 수정하지 마.”

Rules 파일 자체도 커밋해서 수강생과 공유하면 모두가 같은 조건에서 실습하게 된다.

에이전트에게 git 명령을 맡길 때

“커밋해 줘” 정도는 편하지만, reset --hard, push --force, 브랜치 삭제처럼 되돌릴 수 없는 명령은 직접 확인하고 실행한다. 터미널 명령 실행을 허용할 때는 무엇을 실행하려는지 화면에서 읽고 승인하는 습관을 들인다.

10

되돌리기 — Git을 쓰는 진짜 이유

어느 단계까지 갔는지에 따라 방법이 다르다. 지금 어디에 있는지 먼저 확인하고 해당하는 줄을 쓴다.

상황Antigravity에서 / 터미널에서
고치던 파일을 마지막 커밋 상태로 변경 목록에서 파일 우클릭 → 변경 사항 취소
git restore 파일명
＋로 담은 것만 취소 (내용은 유지) 스테이지된 목록에서 − 버튼
git restore --staged 파일명
방금 커밋의 메시지를 고치고 싶다 패널 … 메뉴 → Commit → Undo Last Commit 후 다시 커밋
git commit --amend -m "새 메시지"
방금 커밋을 취소하되 작업은 남기고 같은 Undo Last Commit
git reset --soft HEAD~1
이미 올린(push) 커밋을 안전하게 되돌리기 터미널 권장
git revert 커밋해시
에이전트가 고친 것 전부 취소 “변경 사항” 제목 우클릭 → 모든 변경 사항 취소
git restore .
위험한 두 가지

모든 변경 사항 취소와 git reset --hard는 커밋하지 않은 작업을 확인 없이 지운다. 편집기의 실행 취소(Ctrl+Z)로도 되살아나지 않는 경우가 많다. 누르기 전에 정말 커밋해 둔 지점이 있는지 확인한다.

커밋만 했다면 거의 다 살릴 수 있다

실수로 되돌렸어도 커밋한 적이 있다면 흔적이 남는다. git reflog에서 해시를 찾아 그 시점으로 돌아갈 수 있다. 일단 커밋해 두는 습관이 최고의 안전장치다.

비상용
$ git reflog              # 내가 거쳐온 모든 지점
$ git reset --hard a1b2c3d # 그 지점으로 복귀

$ git stash               # 지금 작업을 잠시 치워두기
$ git stash pop           # 치워둔 작업 꺼내기
파일 하나의 역사만 보고 싶을 때

탐색기에서 파일을 선택하면 아래쪽 타임라인 패널에 그 파일의 커밋 이력이 나온다. 항목을 클릭하면 그때와 지금의 비교 화면이 열린다. 확장 마켓의 GitLens를 설치하면 코드 각 줄 옆에 “누가 언제 왜 고쳤는지”가 표시되어, 에이전트가 쓴 코드와 내가 쓴 코드를 구분하기 좋다.

11

내려받기 — 두 대의 컴퓨터를 오갈 때

학교에서 올리고 집에서 이어서 하려면 순서가 정해져 있다. 이 순서만 지키면 충돌은 거의 나지 않는다.

Clone — 처음 한 번

저장소를 통째로 복제해 새 폴더를 만든다. 기록 전체와 origin 연결까지 함께 온다.

  • 새 컴퓨터에서 처음 시작할 때
  • 남이 공개한 프로젝트를 받아 볼 때

동기화(Sync) — 그다음부터 매번

이미 있는 폴더에 새로 생긴 변경분만 받아 합치고, 내 커밋을 올린다.

  • 작업을 시작하기 전에 한 번
  • 자리를 뜨기 전에 한 번
Antigravity의 ↻ 버튼이 편한 이유

상태 표시줄의 ↻ 1↓ 2↑ 표시는 받을 것이 1개, 보낼 것이 2개라는 뜻이다. 누르면 pull과 push를 순서대로 한 번에 처리한다. 터미널에서 git pull을 잊고 git push했다가 거부당하는 흔한 사고를 이 버튼 하나가 막아 준다.

같은 일을 터미널에서
$ git pull                 # 받아서 합친다
$ git push                 # 내 커밋을 올린다

# 합치기 전에 무엇이 바뀌었는지만 먼저 보고 싶다면
$ git fetch                # 받아만 오고 합치지 않는다
$ git log HEAD..origin/main --oneline
$ git merge origin/main

충돌(conflict)이 났을 때

같은 줄을 양쪽에서 다르게 고치면 Git이 판단을 미룬다. Antigravity에서는 충돌 파일이 변경 목록에 C 표시로 나타나고, 파일을 열면 충돌 구간마다 현재 변경 사항 수락 · 수신 변경 사항 수락 · 둘 다 수락 버튼이 코드 위에 뜬다.

  1. 충돌 파일을 연다

    표시된 구간에서 남길 쪽을 버튼으로 고른다. 양쪽 다 필요하면 둘 다 수락 후 손으로 정리한다.

  2. 표시가 사라졌는지 확인

    파일에 <<<<<<< ======= >>>>>>>가 남아 있으면 아직 끝난 게 아니다. 버튼을 쓰지 않고 직접 지워도 된다.

  3. ＋로 담고 커밋

    해결한 파일을 스테이지에 올리고 커밋하면 병합이 완료된다. 도중에 그만두려면 터미널에서 git merge --abort.

두 대를 오갈 때의 철칙

시작할 때 동기화, 끝낼 때 커밋하고 동기화. 이 순서를 빠뜨리면 양쪽에서 같은 파일을 다르게 고친 상태가 되어 충돌이 난다. 특히 에이전트가 여러 파일을 한꺼번에 고치는 환경에서는 충돌 범위도 넓어진다.

브랜치와 협업

혼자 쓸 때는 main 하나로 충분하다. 하지만 돌아가는 코드를 건드리지 않고 실험하려면 브랜치가 필요하다. 에이전트에게 큰 작업을 맡길 때 특히 그렇다.

Antigravity에서

  1. 브랜치 만들기

    상태 표시줄 왼쪽의 브랜치 이름(예: ⑂ main)을 클릭 → ＋ 새 분기 만들기 → 이름 입력(feature-login). 만들면 자동으로 그 브랜치로 이동한다.

  2. 작업하고 커밋

    평소와 똑같이 ＋ → 커밋. 이 커밋들은 main에 영향을 주지 않는다.

  3. 올리기

    Publish Branch를 누르면 GitHub에 이 브랜치가 올라간다.

  4. Pull Request 올리기

    GitHub 저장소 페이지에 노란 띠와 함께 Compare & pull request 버튼이 나타난다. 눌러서 설명을 적고 만들면 된다.

  5. 합친 뒤 정리

    브랜치 목록에서 main으로 돌아와 동기화. 다 쓴 브랜치는 삭제한다.

같은 일을 터미널에서
$ git switch -c feature-login     # 새 갈래를 만들고 이동
$ git add . && git commit -m "로그인 화면 추가"
$ git push -u origin feature-login

# push하면 PR을 만들 수 있는 링크가 함께 출력된다
remote: Create a pull request for 'feature-login' on GitHub by visiting:
remote:   https://github.com/heejin-park/python-lab/pull/new/feature-login

$ git switch main
$ git pull
$ git branch -d feature-login    # 다 쓴 브랜치 정리
GitHub 화면에서하는 일
Pull requests → New내 브랜치를 main에 합치자고 제안한다. 설명을 적고 리뷰어를 지정한다
Files changed 탭무엇이 바뀌었는지 줄 단위로 보인다. 줄마다 댓글을 달 수 있다
Merge pull request승인되면 이 버튼으로 합친다. 이후 편집기에서 main으로 돌아와 동기화
Issues → New issue할 일·버그를 적어 둔다. 커밋 메시지에 #3을 쓰면 자동 연결된다
Fork남의 저장소를 내 계정으로 복사한다. 오픈소스 기여의 첫 단계
에이전트에게 브랜치를 맡기는 방식

구조를 크게 바꾸는 작업은 브랜치를 먼저 만들어 두고 시킨다. 결과가 마음에 들면 PR로 합치고, 아니면 main으로 돌아와 브랜치를 지우면 된다. “실패해도 흔적이 남지 않는 실험실”을 만들어 주는 셈이라, 더 과감한 지시를 내릴 수 있다.

자주 겪는 문제

소스 제어 패널이 비어 있다

폴더를 열지 않았거나 아직 저장소가 아니다. Open Folder 후 Initialize Repository.

Git not found

Git이 설치되지 않았거나 설치 후 Antigravity를 다시 켜지 않았다. 편집기를 완전히 종료했다 다시 연다.

Please tell me who you are

3장의 user.name·user.email 설정을 하지 않았다.

Support for password authentication was removed

계정 비밀번호로 push를 시도했다. 계정 아이콘에서 GitHub 로그인 또는 gh auth login(5장).

Updates were rejected

원격에 내가 모르는 커밋이 있다. 동기화를 먼저 누른다. 안 되면 git pull --rebase.

refusing to merge unrelated histories

내 폴더와 GitHub 저장소가 따로 시작됐다. git pull origin main --allow-unrelated-histories.

커밋했는데 GitHub에 안 보인다

커밋은 내 컴퓨터에만 저장된다. 동기화를 눌러야 올라간다.

변경 목록에 파일이 수백 개다

.gitignore가 없거나 venv/·data/가 빠졌다. 7장을 먼저 처리한다.

파일이 100MB를 넘어 거부된다

데이터·모델 파일은 올리지 않는다. .gitignore에 넣고 git rm --cached 파일.

실수로 API 키를 올렸다

커밋을 지우기 전에 키부터 폐기하고 재발급한다. 공개 저장소의 키는 몇 분 만에 수집된다.

잔디(contribution)가 안 찍힌다

커밋 이메일이 GitHub 계정 주소와 다르다. git config user.email 확인(4장).

에이전트가 고친 걸 되돌리고 싶다

커밋 전이라면 모든 변경 사항 취소. 커밋 후라면 git revert(10장).

수업 진행 순서 제안

① 터미널에서 git --version과 이름 설정 → ② GitHub 가입·2FA·복구 코드 저장 → ③ 계정 아이콘에서 GitHub 로그인 → ④ 폴더 열고 Initialize Repository → ⑤ .gitignore 만들기 → ⑥ ＋ · 커밋 · Publish to GitHub → ⑦ 웹에서 파일을 고친 뒤 동기화로 받아 오기 → ⑧ 일부러 충돌 만들어 해결 → ⑨ 브랜치에서 에이전트에게 실험 시키기.

⑦과 ⑧을 직접 겪게 하는 것이 핵심이다. 충돌을 한 번 풀어 본 학생은 동기화를 두려워하지 않는다.

기억할 것은 결국 두 줄

맡기기 전에 커밋. 끝나면 확인하고 커밋.

시작할 때 동기화, 자리 뜰 때 동기화.

실습 — 코드 한 개를 만들어 GitHub까지

14장에서 읽은 그 저장소에 새 파일 하나를 직접 추가해 본다. Antigravity에서 코드를 만들고, 키를 안전하게 처리하고, 커밋해서 올리는 한 사이클 전체다.

오늘 만들 것

Gemini에 검색 도구를 켠 채 질문을 던지고 답을 받아 오는 짧은 스크립트다. 파일 이름은 gemini-search-example.py로 한다.

gemini-search-example.py
import os
from google import genai

client = genai.Client(
    api_key=os.environ.get("GEMINI_API_KEY"),   # 키를 코드에 쓰지 않는다
)

tools = [
    {
        'type': 'google_search',
    },
]

generation_config = {
    'max_output_tokens': 65536,
    'thinking_level': 'medium',
}

interaction = client.interactions.create(
    model='models/gemini-3.8-flash',
    input="""클라우드 서비스는 누구의 아이디어인가?""",
    tools=tools,
    generation_config=generation_config,
)

print(interaction.steps[-1])
이 코드에서 눈여겨볼 한 줄

os.environ.get("GEMINI_API_KEY") — 키를 코드에 적지 않고 환경변수에서 꺼내 쓴다. 이 한 줄 덕분에 이 파일은 공개 저장소에 올려도 안전하다. 반대로 api_key="AIza..."처럼 직접 적어 넣으면, 커밋하는 순간 키가 인터넷에 공개된다.

① Antigravity에서 코드 만들기

Editor View에서 에이전트에게 이렇게 시킨다. “키를 어떻게 다룰지”까지 프롬프트에 넣는 것이 요령이다.

프롬프트 예시

google-genai 패키지로 Gemini에 질문을 보내는 파이썬 스크립트를 만들어줘. 검색 도구(google_search)를 켜고, API 키는 코드에 직접 쓰지 말고 환경변수 GEMINI_API_KEY에서 읽어와. 파일 이름은 gemini-search-example.py로 하고, 각 줄에 한국어 주석을 달아줘.

에이전트가 만든 결과가 위 코드와 조금 달라도 괜찮다. 중요한 것은 키를 다루는 방식이며, 다르게 나왔다면 “키를 환경변수에서 읽도록 고쳐 줘”라고 한 번 더 시키면 된다.

② 저장 — 여기서부터 Git이 알아본다

Ctrl/Cmd + S로 저장한다. 탭 제목의 점(●)이 사라지고, 소스 제어 아이콘에 배지가 붙는다. 저장하지 않은 내용은 Git에 보이지 않으므로 커밋이 안 될 때 가장 먼저 의심할 것도 저장 여부다.

③ 키 준비하고 실행해 보기

올리기 전에 돌아가는지부터 확인한다. 내장 터미널(Ctrl + `)에서.

패키지 설치 · 키 설정 · 실행
$ pip install google-genai

# 이번 터미널에서만 쓰는 임시 키 (macOS · Linux)
$ export GEMINI_API_KEY="발급받은_키"
# Windows PowerShell 이라면
> $env:GEMINI_API_KEY="발급받은_키"

$ python3 gemini-search-example.py
.env 파일로 둘 때 — 커밋되지 않는지 반드시 확인

터미널을 새로 열 때마다 키를 다시 넣기 번거로우면 .env 파일에 적어 둔다. 이 저장소는 .gitignore 첫 줄이 .env라 이미 걸러지지만, 확인하는 습관이 중요하다.

무시되는지 확인
$ git check-ignore -v .env
.gitignore:1:.env       .env   ← 규칙이 출력되면 안전하다

# 아무것도 안 나오면 추적 대상이라는 뜻 — .gitignore에 .env를 추가한다

④ 무엇이 바뀌었는지 확인하고 커밋

  1. 소스 제어 패널 열기

    새 파일이므로 gemini-search-example.py 옆에 U(추적되지 않음)가 붙는다. 클릭하면 파일 전체가 추가된 줄(초록색)로 보인다.

  2. 목록을 눈으로 훑기 — 이 단계가 핵심이다

    담기 전에 목록에 있으면 안 될 것이 없는지 본다. .env, 키가 적힌 메모, 실행 결과 파일이 보이면 여기서 걸러야 한다. 올라간 뒤에는 늦다.

  3. ＋로 담고 메시지 쓰기

    “무엇을 했는가”를 한 문장으로. ✨ 버튼으로 생성한 뒤 다듬어도 된다.

    같은 일을 터미널에서
    $ git status -sb
## main...origin/main
?? gemini-search-example.py        ← ?? = 아직 Git이 모르는 새 파일

$ git add gemini-search-example.py
$ git commit -m "검색 도구를 켠 Gemini 질의 예제 추가"
[main 7d9c1a2] 검색 도구를 켠 Gemini 질의 예제 추가
 1 file changed, 27 insertions(+)
  4. 올리기

    상태 표시줄의 ↻ 1↑ 또는 Sync Changes. 터미널이라면 git push.

    올린 뒤 확인
    $ git push
$ git status -sb
## main...origin/main              ← 뒤에 아무것도 없으면 완료
  5. GitHub에서 눈으로 확인

    저장소 페이지를 새로고침하면 파일 목록에 새 파일이 있고, 그 옆에 방금 쓴 커밋 메시지가 붙어 있다. 파일을 열어 키가 그대로 노출되지 않았는지 마지막으로 확인한다.

⑤ 이 실습에서 학생들이 실제로 겪는 실수

키를 코드에 적은 채 커밋

가장 흔하고 가장 위험하다. 커밋을 지워도 기록에는 남으므로, 발견 즉시 키를 폐기하고 재발급하는 것이 먼저다.

저장을 안 하고 커밋

탭에 점(●)이 남아 있으면 저장 전이다. 변경 목록에 파일이 안 보이면 저장부터 확인한다.

실행 결과까지 함께 커밋

출력 파일·캐시는 다시 만들어진다. 목록에 보이면 .gitignore에 넣고 담지 않는다.

커밋만 하고 push를 잊음

“GitHub에 안 보여요”의 대부분이 이것이다. 상태 표시줄에 ↑ 숫자가 남아 있는지 본다.

한 사이클을 요약하면

프롬프트로 만들기 → 저장 → 실행해서 확인 → 목록 훑기 → ＋ → 커밋 → 동기화 → GitHub에서 확인. 예제가 바뀌어도 이 여덟 걸음은 그대로다. 수업에서는 이 실습을 두 번 반복하게 하면 손에 붙는다 — 한 번은 안내대로, 한 번은 학생이 만든 다른 코드로.

16

부록 — 개인 액세스 토큰(PAT) 관리

토큰을 발급받는 것보다 어려운 것은 관리다. 어디에 두고, 언제 바꾸고, 유출되면 무엇부터 하는지. 비밀번호 한 개를 더 갖는 일이라고 생각하면 된다.

먼저 — 토큰이 꼭 필요한가

Antigravity의 계정 로그인이나 gh auth login이 되는 환경이라면 토큰을 만들지 않는 편이 낫다. 그쪽은 만료·보관·폐기를 시스템이 알아서 해 준다(5장). 토큰이 필요한 경우는 대체로 이런 때다.

브라우저 로그인이 막힌 실습실·사내망 · 스크립트나 자동화(CI)에서 push해야 할 때 · 서버처럼 사람이 앉아 있지 않은 곳.

① 두 종류가 있고, 고를 것은 정해져 있다

구분Fine-grained (권장)Classic
접근 범위저장소를 하나씩 골라 지정내가 접근 가능한 모든 저장소
권한Contents·Pull requests처럼 항목별로 읽기/쓰기repo처럼 뭉텅이(scope)로만
만료기본 30일, 최대 366일까지 지정직접 지정. 1년간 안 쓰면 자동 폐기
언제 쓰나거의 모든 경우 — 수업 실습 포함Fine-grained가 지원하지 않는 옛 기능이 필요할 때만
범위를 좁히는 것이 관리의 절반이다

Classic 토큰 하나가 유출되면 내 모든 저장소가 열린다. Fine-grained로 실습 저장소 하나만 지정해 두면, 같은 사고가 나도 피해가 그 저장소에서 멈춘다. 수업에서는 Fine-grained만 쓰게 하는 것을 규칙으로 정해 두는 편이 좋다.

② 발급 — 최소 권한, 짧은 만료, 알아볼 이름

Settings → 맨 아래 Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.

입력 항목이렇게 정한다
Token name어디에 쓰는지 알아볼 이름. 수업노트북-실습저장소-2609처럼 기기 + 용도 + 발급월을 넣으면 나중에 목록에서 헷갈리지 않는다
Expiration수업용이면 30일 이하, 하루짜리 실습이면 7일. “무기한”은 고르지 않는다 — 잊어버린 토큰이 가장 위험하다
Repository accessOnly select repositories를 골라 실습 저장소만 체크. All repositories는 피한다
Permissionspush·pull만 하려면 Contents: Read and write 하나면 된다(Metadata: Read는 자동으로 따라온다). PR까지 만들려면 Pull requests: Read and write를 더한다
토큰은 이 화면에서 딱 한 번만 보인다

생성 직후 github_pat_… 문자열이 한 번 표시되고, 페이지를 벗어나면 다시 볼 수 없다. 그 자리에서 비밀번호 관리자에 저장한다. 놓쳤다면 미련 없이 지우고 새로 만든다 — 복구하는 방법은 없다.

③ 보관 — 한 번만 입력하고 운영체제에 맡긴다

가장 안전한 보관은 내가 들고 있지 않는 것이다. 첫 push에서 한 번 입력하면 운영체제의 자격 증명 저장소가 대신 기억한다.

자격 증명 저장소 지정
# macOS — 키체인에 저장
$ git config --global credential.helper osxkeychain

# Windows — Git 설치 시 함께 오는 Credential Manager
$ git config --global credential.helper manager

# Linux — 15분간 메모리에만 유지(평문 파일 저장을 피한다)
$ git config --global credential.helper "cache --timeout=900"

# 지금 무엇으로 저장되고 있는지 확인
$ git config --global --get credential.helper

두어야 할 곳

  • 운영체제 자격 증명 저장소(키체인 · Credential Manager)
  • 비밀번호 관리자 — 재입력용 사본 하나
  • CI라면 그 서비스의 Secret 저장소

절대 두면 안 되는 곳

  • 코드·노트북 셀·주석 — 커밋되는 순간 끝이다
  • 저장소 주소에 끼워 넣기 (https://토큰@github.com/…) — .git/config에 평문으로 남는다
  • 메신저·이메일·강의 슬라이드·화면 공유 중인 브라우저 탭
  • 공용 PC의 메모장 파일

④ 지금 어디에 저장돼 있나 · 지우기

공용 실습실 PC를 쓴 뒤에는 반드시 지우고 나온다. 다음 사람이 내 계정으로 push할 수 있다.

저장된 자격 증명 삭제
# macOS — 키체인에서 github.com 항목 제거
$ printf "protocol=https\nhost=github.com\n" | git credential-osxkeychain erase
#   또는 '키체인 접근' 앱에서 github.com 검색 → 삭제

# Windows — 제어판 > 자격 증명 관리자 > Windows 자격 증명
#   git:https://github.com 항목 제거

# Linux(cache) — 메모리에 남은 것 즉시 비우기
$ git credential-cache exit

# gh CLI로 로그인했다면
$ gh auth logout

⑤ 교체 — 만료 전에 갈아 끼우기

만료가 가까워지면 GitHub가 메일로 알려 준다. 순서를 지키면 작업이 끊기지 않는다.

  1. 새 토큰을 먼저 발급한다

    기존 것을 지우기 전에 만든다. 반대로 하면 그동안 push가 막힌다.

  2. 자격 증명 저장소를 갱신한다

    위 ④의 방법으로 옛 항목을 지우고, 다음 push에서 새 토큰을 입력한다.

  3. 한 번 push해서 확인한다

    작은 커밋 하나를 올려 새 토큰이 실제로 동작하는지 확인한 뒤에 다음 단계로 간다.

  4. 옛 토큰을 삭제한다

    Settings → Personal access tokens 목록에서 Delete. 확인했으니 미련 없이 지운다.

⑥ 유출됐다면 — 순서가 정해져 있다

폐기가 1순위, 나머지는 그다음

① 즉시 Delete — Settings → Personal access tokens에서 해당 토큰을 지운다. 지우는 순간 그 토큰은 아무 데서도 쓸 수 없게 된다. ② 새로 발급하고 자격 증명 저장소를 갱신한다. ③ 그다음에 커밋에서 지우는 작업을 한다.

순서를 뒤집으면 안 된다. 커밋을 정리하는 동안에도 토큰은 계속 유효하기 때문이다. 그리고 코드에서 지워도 기록에는 남는다 — 그래서 폐기가 먼저다.

GitHub가 대신 잡아 주는 경우도 있다

유효한 토큰이 공개 저장소나 공개 gist에 올라가면 GitHub가 자동으로 그 토큰을 무효화한다. 1년 동안 한 번도 쓰지 않은 토큰도 자동으로 폐기된다.

다만 이건 마지막 안전망일 뿐이다. 비공개 저장소에 올린 토큰이나 GitHub 것이 아닌 키(예: GEMINI_API_KEY)에는 해당되지 않는다. 15장에서 다룬 대로 애초에 커밋되지 않게 하는 것이 본 방어다.

⑦ 수업에서 토큰을 다룰 때

발급 규칙을 먼저 정한다

Fine-grained · 실습 저장소만 · 만료 7~30일 · Contents 권한만. 칠판에 적어 두고 시작하면 중간에 흔들리지 않는다.

화면 공유 중에는 발급하지 않는다

시연할 때는 미리 만든 토큰을 쓰고, 생성 화면은 띄우지 않는다. 녹화본에 남으면 회수가 어렵다.

토큰은 절대 공유하지 않는다

한 사람이 만들어 나눠 쓰면 누가 무엇을 했는지 구분되지 않는다. 각자 발급이 원칙이다.

실습 끝나면 정리하고 나간다

공용 PC에서는 ④의 삭제 명령까지가 실습이다. 마지막 5분을 정리 시간으로 잡아 둔다.

한 장으로 요약

가능하면 만들지 않는다(계정 로그인·gh 우선) → 만든다면 Fine-grained · 저장소 한 개 · 짧은 만료 → 비밀번호 관리자와 운영체제 자격 증명 저장소에만 둔다 → 만료 전에 새 것으로 갈아 끼운다 → 유출되면 폐기부터.
